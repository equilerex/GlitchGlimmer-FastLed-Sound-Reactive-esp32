# mood-vs-events-revamp

Session: 2026-09-21. Status: reframed, not started. The research and the phases live in `2026-09-21-music-model-for-lighting-research.md`; this file holds the problem statement and the facts found about the catalog.

## Context

The owner's complaints about the current mood system: it works but is not intentional, one label is asked to stand for both the overall character of a passage and things that happen in it (build, drop, tease, descent, weird), and bpm as an intensity signal is weak because most songs hold one tempo throughout. In practice most steady dance music reads as the top intensity.

A first version of this plan started from the existing classifier and patched it. The owner rejected that approach twice: music is not a ladder or a fixed path, its characteristics vary independently and can jump anywhere, and a replacement must not be another hidden one-dimensional classifier. The work is now ordered as: research a representation of music for expressive lighting (independent coordinates, trends, structural states, events), test it against real tracks, and only then compare the existing implementation against it.

Direction fixed by the owner, to hold through every phase:

- Mood dimensions are independent coordinates, not ranks and not ordered labels.
- Animation metadata describes where in that multidimensional space an animation works.
- Selection uses multidimensional compatibility plus hysteresis.
- Events are separate from character, so a drop can occur inside any character.
- The current labels, thresholds, scene distribution and animation assignments are not requirements.

## Facts about the catalog and manifest

Recorded because the owner asked and the answer is easy to lose. Phase 3 material: none of it is an input to the research or to phase 2.

- `src/animations/AnimationCatalog.cpp` is the animation library: 37 animations plus a `NONE` slot. Each becomes one scene.
- `web/data/manifest.json` is unrelated to the scene list. It indexes recorded frame dumps for the browser player and is generated by `tools/dump-frames.js`. It has two scenarios, `device` and `moods`. There is no gap to fix.
- Layers are currently chosen from the animation's intensity value alone, so two animations at similar intensity composite alike and identity comes almost entirely from the base animation.

Unchecked, and belonging to phase 3: how many of the 37 are visually distinct rather than recolours, and which of them honour parameters such as speed, palette and spread. That decides whether a few animations can be driven continuously by the coordinates or whether many discrete ones must be selected between.

## Build order

A review pass rewrote this section into an implementation sequence — coordinates, selection machinery, layers, then an audit of the 37 animations. The owner rejected it, for the same reason the first version of this plan was rejected twice: it anchors on the existing implementation before the music model is understood. The phase order stands.

1. Phase 1, research. The durable model is `docs/music-research/MODEL.md`; the dated research plan holds this iteration's scope and feasibility. Understand what aspects of live music are worth representing for expressive lighting.
2. Phase 2, real captures, marked by ear first and compared against the signals after. Test whether cheap proxies are good enough in practice. A concept is dropped here, on evidence, or not at all.
3. Phase 3, compare the implementation to what phase 2 measured and decide keep, replace or reinterpret.
4. Only then design the animation-side region metadata, the selection and hysteresis, and the event set.

The engineering plan for the rebuild itself is `2026-09-21-music-engine-rebuild.md`. It found that the signals this revamp wants already exist in `AudioFeatures` and that `classifyMood()` is what collapses them, so steps 1 to 3 there are an information-preserving refactor that can start before phase 2 finishes. Its step 4 is the part gated on evidence, and it is the same step 4 above.

The wearable scope set in the research plan narrows *how precisely* things must be inferred and which timescales are available. It does not shorten this order and it is not licence to skip to step 4.

**One exception, and it is not a design decision.** The signal path needs fixing regardless of what phase 2 concludes: analysed blocks carry no timestamp and the LED frame steals the audio hop, which breaks every rate and periodicity measure — onset rate, flux, pulse strength, tempo, beat phase. Details in the research plan under "Signal-path limits that are already fixed". It can be done at any time and blocks phase 2 from producing trustworthy device-side traces, so doing it early is free.
