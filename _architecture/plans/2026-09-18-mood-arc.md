# mood-arc

Session: 2026-09-18. Status: planned, not started. Not reviewed against a real capture yet.

## Context

The reported symptom is that the mood "keeps jumping between calm and energetic or calm and intense", and that those changes are too abrupt, with steps missing in between.

Investigation found the cause is not a missing transition. It is a **dead band wired to a randomiser**.

`MoodHistory::classifyMood` (`src/scenes/MoodHistory.h:304-331`) tests four overlapping booleans and returns `UNKNOWN` when none of them holds. Enumerating the coverage leaves four large holes:

| level | bpm | result |
|---|---|---|
| >0.8 with dynamics not above `dynHigh` | any | UNKNOWN |
| 0.60-0.80 | <=100 | UNKNOWN |
| 0.40-0.60 | >=80 | UNKNOWN |
| 0.30-0.40 | any | UNKNOWN |

`UNKNOWN` reaches `SceneRegistry::pickSceneByMood`, which randomises in two places (`src/scenes/SceneRegistry.cpp:52` and `:54`). The `:54` fallback is `scenes[random(scenes.size())]`, a uniform draw over all eight scenes. In any hole the scene is therefore redrawn at random. On top of that `moodToString` maps `UNKNOWN` to `"Calm"` (`MoodHistory.h:16-25`), so the display reports calm while the picker draws at random.

There is a second, separate cause of the abruptness. **There is no crossfade anywhere in the scene path.** `SceneState::beginScene` resets the clock and the strip is repainted on the next frame, so every mood change is an instant cut. Even a correct change reads as jarring.

The owner's brief, including two corrections made to the first design pass:

- The ten-mood lineup is **silent, floaty, calm, tease, dancy, buildup, energetic, DROP, intense, Weeeeird**.
- **Moods are tracked sections, not a forced ladder.** Music bounces back and forth, teases a drop and returns to dancy, and jumps from floaty straight to intense. The ladder is an ordering used for matching, never a path the classifier is forced to walk one rung at a time. A step limiter was designed and explicitly rejected.
- **Animations are an open set.** Do not hardcode a port list. Define what a mid-intensity EDM section is, then score candidates against that, so the set can keep growing.
- **Ported animations go in near-static, and the layers make them alive.** The layer system supplies reactivity, so a port needs no audio work of its own.
- **A mood with no animation defined is skipped, not randomised.**
- Order of work: moods first, then the defects in the current system, then the animations.

The intended outcome is a classifier that names the section a track is actually in, a scene choice that is deterministic, and a catalog with something to play at every intensity rather than only at the top.

## What is actually broken

Verified against source. Fixing these is a stated part of the request, not incidental cleanup.

2. **Four dead bands** in `classifyMood`, listed above.

## The mood model

### The enum

`src/scenes/MoodHistory.h:8-14`, in the owner's display order:

```cpp
enum MoodType {
    SILENT, FLOATY, CALM, TEASE, DANCY,
    BUILDUP, ENERGETIC, DROP, INTENSE, WEIRD,
    MOOD_COUNT   // sentinel, never a mood, never returned by classifyMood
};
```

`MOOD_COUNT` exists so the three hardcoded `5`s cannot be forgotten again.

Two consequences worth writing into the code, because both will be tripped over:

- **The enum is not intensity-ordered.** Display order interleaves structural moods with ladder moods, so comparing enum values does not compare intensity. Every rank comparison goes through `ladderRank()`.
- **`MOOD_COUNT` is not a mood.** It must never be returned, never selected, and `moodToString(MOOD_COUNT)` returns `"?"`.

`moodToString` gets all ten cases, `WEIRD` returning `"Weeeeird"`, and the dead `return "Unknown"` goes.

### A total ladder replaces the four booleans

This is the dead-band fix. An ordered chain with an `else`, so the partition is total by construction:

```cpp
LADDER_EDGE_0 = 0.20f;   // FLOATY    | CALM
LADDER_EDGE_1 = 0.40f;   // CALM      | DANCY
LADDER_EDGE_2 = 0.60f;   // DANCY     | ENERGETIC
LADDER_EDGE_3 = 0.80f;   // ENERGETIC | INTENSE
```

`level` is clamped to 0..1 at `src/audio/AudioProcessor.cpp:396` before it reaches a snapshot, so every value falls in exactly one band.

**`bpm` and `dynamics` are nudges, not gates.** Each can move the rung by at most one, then the result is clamped to 0..4:

- `bpm > 120` nudges up, `1 < bpm < 80` nudges down. The `bpm > 1` guard is required, because `bpm` is exactly 0 whenever no tempo is known (`AudioProcessor.cpp:508-513`) and a bare `bpm < 80` would permanently push down every beatless passage.
- `dynamics` against the existing `dynLo`/`dynHi` cuts nudges up or down, only when `dynSpan > DYN_MIN_SPAN`.

This is precisely why the holes close. The old form was `energetic = level > 0.6 && bpm > 100`, which made level 0.5 unreachable no matter what. A gate removes a band from the ladder, and a removed band is a dead band. A nudge of at most one rung cannot create one.

The honest reading of the evidence: on the one real capture, `level` spans 0.04-0.83 while `dynamics` spans only 0.00-0.26, so the dynamics nudge will often be inert on this microphone. Level carries the ladder, bpm sharpens it, and dynamics refines it only where there is a range to refine.

`held` is deleted from the classifier. It existed only because the four overlapping booleans could both be true, and a total partition has nothing to disambiguate. The signature becomes a pure `classifyMood(const MoodSnapshot&)`.

### No forced step walk

The ladder is an ordering, never a path. A mood may jump from FLOATY straight to INTENSE, and that is correct, because a track can do exactly that.

Entry and exit keep the mechanisms already present: `confirmMs = 500` (`MoodHistory.h:123`) and `minHoldMs = 2000` (`:122`), both unchanged. They prevent chatter on a threshold, which is all they were ever for.

The abruptness is answered in two other places, and both are real defects rather than missing machinery. The randomiser made the scene wrong (see below), and the instant cut made the change hard (see the crossfade step).

`predictNextMood` (`MoodHistory.h:333-354`) extends to the new fields. Two traps to encode: the averaged `gateGain` must be the ring's mean, since leaving it at the struct default makes a prediction about a silent window claim signal, and `dropDetected` must be forced `false`, because a one-frame pulse has no meaningful mean.

### Deterministic scene selection

`SceneRegistry::pickSceneByMood`, rewritten. Both `random()` calls go.

Use the two catalog fields that have been declared and unread since the catalog was written: `AnimationMeta::intensity` and `preferredTempo` (`src/animations/AnimationCatalog.h:21-41`). Nothing in the firmware reads them today.

Selection, in order:

1. **Structural override.** A structural mood (`SILENT`, `TEASE`, `BUILDUP`, `DROP`, `WEIRD`) uses a scene tagged for it, if one exists. `SceneDefinition::preferredMoods` is renamed `structuralMoods` for this narrowed meaning. A ladder-valued tag in it is inert, or Alien Breath's `CALM` tag would win every CALM pick and the intensity axis would never be consulted.
2. **Nearest intensity.** Otherwise take the scene with the smallest `|intensity - targetIntensity(mood)|`.
3. **Drop the running scene** while another candidate remains, preserving the rule at `:46-49` so a transition is always a real change.
4. **Tempo tie-break**, then catalog index. `preferredTempo` is 0..1 and `bpm` is 60..180, so normalise with the same `/130.0f` the scene clock uses (`src/scenes/SceneState.cpp:43`). Comparing them raw would make the tie-break a constant, which is a silent way of making it do nothing.

The result is deterministic, total, and testable, with `random()` off the selection path entirely. A mood whose candidate set is empty leaves the current scene running, which is the "skip it" behaviour the owner asked for. Because every mood carries a default intensity target, that is rare in practice.

### Structural detectors

New state lives in `AudioProcessor`, beside the beat and tempo state, exposed on `AudioFeatures`. Not derived from `AudioHistory`, which is about 17 s and far too short for a buildup that runs 15-60 s.

`AudioFeatures` has **no `gateGain` field today**, only the bool `signalPresence`. Add:

```cpp
float gateGain = 1.0f;          // defaults to 1.0f, see below
float buildup = 0.0f;
bool  dropDetected = false;     // one-frame pulse
float spectralFlatness = 0.0f;  // computed and discarded today
float anomaly = 0.0f;
bool  teaseDetected = false;
```

**`gateGain` must default to `1.0f`, not `0.0f`.** The harness builds `AudioFeatures` by hand in `scriptedAudio()` (`sim_main.cpp:161-191`) and in every fixture, and none of them would set a new field. A `0.0f` default makes every scripted frame read `SILENT` and breaks five checks at once. Same rule as `pixelLevel()` being a method rather than a field (`AudioFeatures.h:20-27`): a producer that forgets must get normal behaviour, not a dead strip. `MoodSnapshot`'s default constructor follows.

`AudioSnapshot` is deliberately **not** changed. `AudioHistory` holds 1500 entries, and four more floats would add 24 KB of permanently-resident heap to a ring whose deepest live consumer reads the last 10. No layer needs them.

**SILENT.** No new detector. `gateGain` already exists and is already ramped at `GATE_RAMP 0.04f` (`AudioProcessor.cpp:314`). Expose it, and classify `SILENT` when `gateGain < 0.5f`. It is debounced by its own ramp, so a signal sitting on the presence threshold cannot chatter.

**BUILDUP.** Displacement above the signal's own slow mean, which is a different measurement from `dynamics`. Track a slow symmetric follower of `level` (tau about 3 s), then `buildupRaw = level - slowEnv`. Require it above 0.15 for 1500 ms with a climb of at least 0.10, plus a 3 s cooldown, so a plateau does not re-enter on every dip.

Why this is not `dynamics`: `dynamics` is `(dynHi - dynLo)/dynHi` over `levelEnv` (`AudioProcessor.cpp:367-377`), the **width of the window the envelope has covered**. It is equally large on a fall as on a rise, and it stays large once the rise stops. `buildup` is **displacement above the recent mean**, positive only while still climbing, decaying to zero within about 3 s. A track loud for a minute has high `dynamics` and zero `buildup`. A track climbing has both.

Gate it to `ladderRank < 3` in the classifier, so a rising passage already at ENERGETIC is just loud music rather than a sticky BUILDUP.

**DROP.** Four conditions, none of which a beat can satisfy:

1. **Breadth.** All three of `bassLevel`, `midLevel` and `trebleLevel` above 0.60. A beat is low-end only, which is exactly what `BEAT_BASS_RISE 1.15f` at `AudioProcessor.cpp:476` exploits to tell rhythm from voice. A kick cannot light all three bands at their own recent maxima. A drop does it by construction.
2. **Scale.** `level - slowEnv > 0.35` in one block, strictly larger than the buildup threshold.
3. **Preceding quiet.** `slowEnv < 0.55`. The last few seconds were not already loud. This is what stops a drop firing mid-chorus, and it encodes the musical fact that drops follow a breakdown or a buildup.
4. **Persistence and rarity.** 400 ms of sustained arming, then an 8 s cooldown. At most one drop per 8 s, so the mood cannot park there.

Because `dropDetected` is a one-frame pulse, `MoodHistory` pins the display for about 3 s after it fires, or `confirmMs` would reject it before it could be shown. The pin lives in `update()`. `classifyMood` itself stays pure.

**TEASE.** The owner chose the broadest reading: all three interpretations as one tension state. So tease is **tension without full energy**, a composite, and any one trigger suffices:

- **post-drop breakdown**: a DROP fired within the last 12 s, the gate is open, and the beat continues
- **pre-drop hush**: `buildup` is forming or `dynamics` is rising while `level` sits low
- **fake-out**: `level` variance over about 1 s exceeds a threshold while the 1 s mean stays mid. Pulses do not sustain.

Gate on `ladderRank < 3`, plus a minimum hold and a cooldown. This is the fuzziest of the five detectors and the one most likely to need retuning on a real capture. Its constants live together at one site so they can be moved without hunting.

**WEIRD.** Two of these three, each a rate of change or a band membership rather than a level, so a stable passage scores zero whatever its spectrum:

- **centroid off its own mean**: `spectrumCentroid` more than 60 percent of its own recent span from its slow mean. A span floor matters, or a steady tone with a near-zero span produces a huge ratio against a tiny denominator.
- **tempo present but unstable**: spread of the existing 12-entry `beatIntervals` ring (`AudioProcessor.h:33`) over 0.35 of its median, requiring at least 6 intervals. Four-on-the-floor sits under 0.15, where breakcore and glitch run over 0.4. This is the strongest eclectic signal available and it costs one pass over twelve numbers.
- **flatness in the middle band**: `spectralFlatness` between 0.15 and 0.45. Below is plainly tonal, above is plainly a room or a cymbal wash.

Plus a 2.5 s hold, a 4 s cooldown, and reachable only from DANCY up, so a quiet drifting ambient passage is CALM rather than WEIRD.

**Classifier shape**, two stages:

```cpp
if (gateGain low)                  return SILENT;
if (dropDetected)                  return DROP;
if (teaseDetected)                 return TEASE;
const int r = ladderRankFrom(m);
if (anomaly high && r >= 2)        return WEIRD;
if (buildup high && r < 3)         return BUILDUP;
return rankToMood(r);
```

A `classifyForTest` seam exposes the raw verdict so the harness can sweep the whole input space without the dwell.

## Fixing the defects

Ordered by the owner: moods, then defects, then animations. Three notes on how:

- **Inert Config macros.** Either wire them or delete them. Recommendation: delete `NOISE_THRESHOLD`, `MAX_AUDIO_LEVEL`, `LOUDNESS_SMOOTHING` and `FFT_SMOOTHING`, and make `GAIN_SMOOTHING` the single source for the value currently hardcoded at `AudioProcessor.h:22`. A macro that disagrees with the code that runs is worse than no macro.
- **Twelve dead layers.** Add the twelve `LayerType` values and the twelve cases in `addLayerByType`, but **fix the two defects first**: make `DominantBandTrailLayer`'s heat array a member, and give `DynamicsFlickerStormLayer` an opacity floor. Then vary `SceneDefinition::layerTypes` per band, so low bands and high bands do not composite identically. Keep the total at or under `kMaxLayers = 4`, and add the missing cap guard in `applySceneLayers`, since `addLayerByType` does not enforce it when called directly.
- **Hardcoded `5`s** become `MOOD_COUNT`.

## Animations, as an open set

### The tonal brief

The owner asked what a medium-intensity part of an EDM track *is*, rather than which file to port. This is the thing to score candidates against.

A mid-intensity section is the groove, not the peak:

- A steady regular pulse at 110-128 BPM is present.
- Motion is continuous and legible: travelling waves, drifting gradients, rotating structure. Not per-pixel noise, not strobing.
- Temporal rate is beat-scaled, roughly 0.5-2 Hz. Nothing modulated at 10 Hz.
- Contrast is mid. Nothing reaches full black or full white, and the strip never blanks.
- Palette is 2-4 related hues, not full-spectrum chaos and not one flat colour.
- Spatial structure is whole-strip and reads as a single gesture.
- Cost is low per pixel, because layers composite on top and share the frame budget.

### The fit criterion

Any candidate, from either project, passes or fails on five points:

1. Coherent spatial structure with one readable gesture.
2. Temporal motion in the 0.5-2 Hz band.
3. Mid contrast, no hard on/off, no full-strip flash.
4. Palette narrow and mid-value.
5. O(N) per frame, no per-pixel transcendentals, no allocation.

### The starting pool, scored

Not a fixed list. The set stays open, and the criterion above is what admits new entries.

**In-repo, already written, unreachable, zero porting cost:** `TriwaveBeatLayer`, `EnergySpiralLayer`, `CentroidColorFlowLayer` and `DominantBandTrailLayer`. These are the strongest first move, because they are layers already, so they compose natively and need no interface adapter.

**From the Serenity project, by fit:** `EtherealPlasmaDrift` (best engineered of the set, O(N), no allocation, palette morphed in place, and it has a free pulse slot), `ColorWavesAnimation`, `AuroraAnimation`, `TwilightRippleAnimation`, `StarlitDriftAnimation`, `PlasmaEffectAnimation`, `DreamwaveAuroraAnimation`, `MoonlightAnimation`.

**Not suitable as an ambient base, and why**, so the reason survives: `BeatDropAnimation` is a three-phase drop envelope (pulse fill, full white, fading sparkles), which is a hard on/off and a full-strip flash, so it fails point 3. It is useful later as a *transient* on the DROP mood specifically, not as a base.

### The port method

Nothing in the Serenity project is liftable as-is. Its `AnimationBase` has a different interface (`update()` takes no arguments, the buffer and length arrive at construction, plus `setBrightness`, `setColorModifier` and `addGlitter`), it is `-std=gnu++17`, and **none of its 52 animations reads audio at all**. Its `beatsin8` calls are free-running oscillators, not detectors.

A port is therefore a thin adapter: an `Animation` subclass (`src/animations/Animation.h`, one pure virtual `update(CRGB*, int, const AudioFeatures&)`) holding the Serenity render body. C++17 constructs to rewrite for gnu++11: designated initializers, `std::clamp`, `std::make_unique`. `pio run` is the only build that catches these, since the harness compiles at a newer standard.

**One correction to "keep them literally static".** Spatial motion can ignore audio entirely, and the layers will supply the life. Global brightness cannot, because a base that ignores audio renders at full brightness in silence. So every port scales its output by `pixelLevel()` for a `CRGB` sink or `hsvLevel()` for a `CHSV` val. That is one line per port, and handing the wrong one to a `CHSV` val renders black with no error (`AudioFeatures.h:28-45`). Static means no spatial audio reaction, not no audio at all.

Then wire the accents. A ported drifting wave under `BassShockwaveLayer`, `BeatFlashSparkLayer` and a newly reachable `TriwaveBeatLayer` reads as reactive while the base knows nothing about audio. Verify on the live page before deciding any base needs more.

## Making a change read as a change

Small, separately droppable, and it answers the original complaint directly.

- **The mood stays honest.** The mood model and the defect sweep above do this. No randomiser, no dead bands, no lying display string.
- **A short crossfade on scene change.** There is none today, which is why every correct change is also a hard cut. A blend over roughly 300-500 ms in the scene path makes a jump read as intentional. This is the only place a crossfade belongs: the owner wants jumps to be possible, so the fix is to make them not jarring rather than to prevent them.
- **Per-mood frame share in the browser HUD.** That is the number the whole feature exists to move, and a session sitting at 95 percent in one mood should be visible.

## Verification

**Before anything else: record a 60-120 s capture of a real track** through the live page's Record button into `docs/`. The only real capture is 2.3 s, shorter than `minHoldMs` and shorter than every new window, so the arc cannot be verified at all without it. Per `AGENTS.md`, do not tune against the synthetic demo signal.

New harness checks in `src/sim_main.cpp`:

- **Totality sweep.** 101 `level` values x 8 `bpm` x 5 `dynamics` x 2 `dynSpan` x 3 `gateGain`, all through `classifyForTest`. Assert every input returns a real mood, that every mood except the structural ones is produced at least once, that rank never decreases as `level` rises with everything else fixed, and that `gateGain = 0` returns `SILENT` for all of them. The non-vacuity assertion is the one that would have caught the original bug.
- **Drop is not a beat.** A synthetic 128 BPM kick fires `beatDetected` many times and `dropDetected` zero times. A broadband slam after a quiet passage fires it exactly once, and not again inside the cooldown.
- **Weird is rare.** A steady tonal block and a steady broadband block both produce zero `WEIRD`. A genuinely eclectic block produces it, and not again inside the cooldown.
- **The picker is deterministic.** The same state gives the same pointer 100 times. Two different `randomSeed` values give the same pointer. Re-picking with the winner already active returns a different scene.

Existing checks that must change: the `UNKNOWN` sentinels become a `havePrev` flag, the two `for (i < 5)` loops and `moodFrames[5]` become `MOOD_COUNT`, the `INTENSE` assertion at `sim_main.cpp:1329-1344` is rewritten around intensity since `INTENSE` is now a ladder mood, and `scriptedAudio` sets `gateGain`.

End to end: `pio run` (the only build that checks device-reachability at gnu++11) and `pio run -e native -t exec` both green, then `npm start` against the new capture, watching the mood step through neighbours rather than cut, and reading the per-mood frame share.

## Implementation deviations

- Pacifica is a thin wrapper around FastLED's `fx/1d/pacifica.h`, not a Serenity port. That header defines members out of line with no `inline`, so `PacificaAnimation.h` is included only from `AnimationCatalog.cpp`. Including it from `AnimationCatalog.h` failed the device link with duplicate `fl::Pacifica` symbols.
- Compositor classes moved to `src/animations/visual-layers/` so they are not listed next to catalog bases. The plan's `src/animations/VisualLayers.h` path is the old one.
- Aurora (Serenity) and Pacifica (FastLED) are in the catalog. The unused-layer accents and the rest of the C2 set are still open.
- FastLED 3.10.3's 1D effects live at `fx/1d/`, not `fl/fx/1d/`. Catalog adapters wrap the shipped class and scale with `pixelLevel()`. Pacifica, NoiseWave and Fire2012 are in. Pride2015 is not: full-spectrum rainbow fails C2 palette. DemoReel100 is not: cycling looks is the scene director. Fire2012's default `HeatColors_p` ends in white, so the wrapper passes an amber palette into the constructor rather than rewriting the fire.
